# Deployment

Takeout supports multiple deployment strategies to fit your needs. This guide covers deployment options, considerations, and best practices.

## Deployment Options

Takeout can be deployed to:

1. **AWS with SST** - Full-featured, production-ready (recommended)
2. **Uncloud** - Simplified deployment platform
3. **Custom Docker** - Deploy anywhere with Docker support

## Architecture Overview

A complete Takeout deployment includes:

### Core Services

**Web Application**
- One.js server for web app and API routes
- Serves static assets
- Handles authentication
- Routes API requests

**Zero View Syncer**
- Serves client queries
- Manages WebSocket connections
- Auto-scales based on load
- Runs on port 4848

**Zero Replication Manager**
- Monitors PostgreSQL for changes
- Streams changes to view syncers
- Handles database backup
- Critical for real-time sync

**PostgreSQL Database**
- Primary data store
- Logical replication enabled
- Contains: main DB, Zero CVR, Zero CDB

### Supporting Services

**Load Balancer**
- Routes traffic to services
- SSL/TLS termination
- Health checks

**CDN (CloudFront)**
- Serves static assets
- Caches responses globally
- Reduces latency

**Object Storage (S3/R2)**
- User uploads (images, videos)
- Database backups
- Application assets

## Pre-Deployment Checklist

Before deploying to production:

### 1. Environment Configuration

```bash
# Review and update all environment variables
cp .env.production.example .env.production

# Required variables:
BETTER_AUTH_SECRET=<generate-with-openssl-rand-hex-32>
BETTER_AUTH_URL=https://yourdomain.com
ONE_SERVER_URL=https://yourdomain.com

# Database (managed by deployment)
ZERO_UPSTREAM_DB=<auto-configured>
ZERO_CVR_DB=<auto-configured>
ZERO_CHANGE_DB=<auto-configured>

# Storage
CLOUDFLARE_R2_ENDPOINT=<your-r2-endpoint>
CLOUDFLARE_R2_ACCESS_KEY=<your-access-key>
CLOUDFLARE_R2_SECRET_KEY=<your-secret-key>

# Email
POSTMARK_SERVER_TOKEN=<your-postmark-token>

# Analytics (optional)
VITE_POSTHOG_API_KEY=<your-posthog-key>
VITE_POSTHOG_HOST=<your-posthog-host>
```

### 2. Update Constants

Edit `src/constants/app.ts`:

```typescript
export const DOMAIN = 'yourdomain.com'
export const APP_NAME = 'Your App Name'
export const APP_NAME_LOWERCASE = 'yourapp'
```

### 3. Configure OAuth

For each OAuth provider:

1. Update redirect URLs to production domain
2. Add production credentials to environment
3. Test OAuth flow in staging first

### 4. Database Migrations

Ensure all migrations are ready:

```bash
# Generate migration files
bun tko db generate

# Review migration files
ls -la src/database/migrations/

# Test migrations locally
bun migrate
```

### 5. Build Test

Test production build locally:

```bash
# Build web app
bun tko web build

# Test production mode
bun tko web prod
```

### 6. Run Full Test Suite

```bash
# All tests
bun test

# CI checks
bun tko check --all
```

## Deployment Strategies

### Blue-Green Deployment

Deploy new version alongside old, then switch traffic:

1. Deploy new version to staging
2. Run smoke tests
3. Switch traffic gradually
4. Monitor for errors
5. Roll back if needed

### Rolling Deployment

Update instances one at a time:

- Minimizes downtime
- Allows quick rollback
- Built into ECS deployment

### Canary Deployment

Route small percentage of traffic to new version:

1. Deploy new version
2. Route 5% traffic to new version
3. Monitor metrics
4. Gradually increase percentage
5. Complete rollout or rollback

## Monitoring

### Health Checks

All services include health endpoints:

```bash
# Web app health
curl https://yourdomain.com/api/health

# Zero health
curl https://zero.yourdomain.com/
```

### Logging

View application logs:

```bash
# SST deployment
bun tko aws logs webapp
bun tko aws logs zero

# Uncloud deployment
bun tko uncloud logs
```

### Metrics

Monitor key metrics:
- Response time
- Error rate
- Database connections
- Memory usage
- CPU usage
- Active WebSocket connections

### Alerts

Set up alerts for:
- Service health check failures
- High error rates (>1%)
- High response times (>1s)
- Database connection exhaustion
- Memory/CPU > 80%

## Rollback Strategy

### Quick Rollback

If deployment fails:

1. Identify issue from logs
2. Roll back to previous version
3. Investigate and fix
4. Redeploy when ready

### SST Rollback

```bash
# Deploy previous version
git checkout previous-tag
bun tko sst deploy production
```

### Container Rollback

```bash
# Deploy specific image version
WEB_APP_DOCKER_IMAGE=your-registry:previous-tag bun tko sst deploy production
```

## Security Considerations

### Secrets Management

- Use environment variables for secrets
- Never commit secrets to git
- Rotate secrets regularly
- Use AWS Secrets Manager or similar

### Network Security

- Enable VPC for database isolation
- Use security groups to restrict access
- Enable SSL/TLS for all connections
- Configure CORS properly

### Database Security

- Enable encryption at rest
- Use SSL for connections
- Regular backups (automated)
- Enable deletion protection
- Restrict database access to VPC only

### Application Security

- Validate all user input
- Use prepared statements (Drizzle does this)
- Implement rate limiting
- Enable CSRF protection (Better Auth includes this)
- Keep dependencies updated

## Cost Optimization

### Development Stage

Use cost-saving options:

```typescript
// sst.config.ts
capacity: 'spot',           // Use spot instances
scaling: { min: 0, max: 1 }, // Minimal scaling
```

### Production Stage

Balance cost and reliability:

```typescript
capacity: 'on-demand',      // Reliable instances
scaling: { min: 1, max: 5 }, // Auto-scale as needed
```

### Database Optimization

```typescript
// Aurora Serverless v2 scales automatically
scaling: {
  min: '0 ACU',   // Scale to zero when idle
  max: '4 ACU',   // Max capacity
}
```

### Monitoring Costs

- Review AWS Cost Explorer weekly
- Set up billing alerts
- Optimize based on usage patterns
- Consider reserved instances for steady load

## Staging Environment

Create staging environment:

```bash
# Deploy to staging
bun tko sst deploy staging
```

Configure staging-specific settings in `sst.config.ts`:

```typescript
const isProduction = input.stage === 'production'

// Use different domains
domain: isProduction ? 'app.com' : 'staging.app.com'

// Use smaller instances for staging
cpu: isProduction ? '4 vCPU' : '1 vCPU',
memory: isProduction ? '8 GB' : '2 GB',
```

## Continuous Deployment

### GitHub Actions

Example workflow (`.github/workflows/deploy.yml`):

```yaml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: oven-sh/setup-bun@v1
      - run: bun install
      - run: bun test
      - run: bun tko check --all
      - run: bun tko sst deploy production
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
```

### Deployment Pipeline

1. **Code pushed** to main branch
2. **Tests run** (unit + integration)
3. **Build** production artifacts
4. **Deploy** to staging
5. **Smoke tests** on staging
6. **Deploy** to production
7. **Health checks** verify deployment
8. **Rollback** if health checks fail

## Troubleshooting

### Deployment Fails

1. Check deployment logs
2. Verify environment variables
3. Ensure migrations are compatible
4. Check resource limits

### Services Won't Start

1. Review health check configuration
2. Check application logs
3. Verify database connectivity
4. Ensure all secrets are set

### High Error Rates

1. Check application logs
2. Review recent changes
3. Monitor database performance
4. Check external service status

### Slow Performance

1. Review database queries
2. Check for N+1 queries
3. Verify CDN configuration
4. Monitor resource utilization
